# Обработчики: свой код по событию изменения


## Общий принцип действия
Репликтор пишет в базу изменения, которые летят из 1С. 
Также Репликатор может периодически по расписанию или по запросу делать перевыгрузки данных.
Если данные в базе отличаются от полученных, то произойдет обновление и заполнится метка времени merged_on - дата и время, когда данные последний раз изменились.

Далее у нас 2 задачи:
- Вызвать обработчик - для этого у каждого обработчика прописан список обеъектов на которых он реагирует (`ON`).
- Внутри обработчика написать код, который правильно заберет измененные данные и дальше обновит витрину или выполнит еще что-то (`handle`). 

Вызов обработчика и различная обвязка вокруг реализована в модуле. Сам код пишет пользователь в зависимости от того, какую витрину строит или какие дальнейшие действия нужно выполнить с данными.

## 1. Простейший обработчик

Обработчик — обычный python-класс. Нужны две вещи: на что он подписан (`ON`) и что делать
(`handle`). 
Сам файл обработчика нужно положить в папку `handlers`.

```python
from cdc_1c import Handler1C

class ZakazyKlientov(Handler1C):
    # имена ТАБЛИЦ в целевой БД (транслит), а не имена объектов 1С
    ON = ["AccumulationRegister_ZakazyKlientov", "Catalog_Nomenklatura"]

    def setup(self, context):        # один раз за процесс: DDL витрины и вьюшек
        self.execute(context, DDL)

    def handle(self, context):       
      # полезная работа
```

Далее в `runner.py` подключить обработчик с помощью `import` и запустить поток.

```python
from cdc_1c import HandlerLoop
from handlers import ZakazyKlientov

handler_zakazy = HandlerLoop(engine=engine, schema="cdc_1c", handler=ZakazyKlientov())

with ThreadPoolExecutor(max_workers=2) as pool:
    pool.submit(handler_zakazy.run_forever)
```

## 2. Окно изменений — главное понятие

**Данные обработчику не передаются.** Ему передаётся окно времени, за которое надо отработать, а
`SELECT` он делает сам:

```sql
WHERE merged_on > :last_run_at
```

Таким образом, он не зависит от того, каким путём данные обновлены — изменением или
полной выгрузкой.

### Что лежит в `context`

| поле `context` | что это |
|---|---|
| `last_run_at` | отметка предыдущего **успешного** прогона; `None` — с начала времён |
| `boundary` | верхняя граница окна: то, что станет `last_run_at` в следующий раз |
| `full_rebuild` | витрину просят собрать заново (см. §6) |
| `rebuild_from` | метка последнего завершённого блока пересборки (см. §6) |
| `engine`, `schema`, `temp_schema` | подключение и схемы |
| `logger` | логгер обработчика |

Обе границы — по часам БД (тем же `now()`, которым `dbmerge` проставляет `merged_on`), поэтому
расхождение часов между хостами роли не играет.

### Почему в `WHERE` нет верхней границы

Окно закрыто справа, но писать `merged_on <= :boundary` не нужно: библиотека сама выбирает границу
так, чтобы ничего не пропустить. Самое плохое, что может случиться, — строка попадёт в расчёт на
один прогон раньше срока и пересчитается ещё раз в следующем окне. Это лишняя работа, а не потеря.

Верхнюю границу имеет смысл добавлять только там, где повтор дорог сам по себе — например, при
отправке во внешнюю систему.

## 3. Как писать саму витрину

1С хранит данные нормализованно: чтобы дотянуться из регистра заказов до кода товара, нужен `JOIN`
со справочником номенклатуры по guid. Для задач DWH обычно нужна менее строгая нормализация, поэтому
в [config/handlers/](config/handlers/) лежат два разобранных примера инкрементальной витрины:

- [zakazy_klientov.py](config/handlers/zakazy_klientov.py) — ключ таблицы фактов сохраняется (строки
  регистра как есть, плюс артикул из справочника);
- [zakazy_klientov_grouped.py](config/handlers/zakazy_klientov_grouped.py) — ключ меняется
  (`GROUP BY` по номеру документа, году и артикулу), пересчёт остаётся инкрементальным, а ключ
  группы составной — видно, как это отражается на фильтрах (`tuple_(a, b).in_(...)`).

**Отметка времени нужна от каждого участника `JOIN`.** Оба примера построены на одном правиле:
вьюшка отдаёт `merged_on` каждого источника отдельной колонкой (`merged_on`,
`Nomenklatura_merged_on`, …), и в инкремент попадает всё, что стало свежее хотя бы по одному из них.

Так надо потому, что объекты 1С приезжают в обмене независимо и в произвольном порядке: справочник
номенклатуры может доехать или измениться позже регистра. Если ориентироваться только на `merged_on`
регистра, такая строка в инкремент не попадёт, и витрина навсегда останется с `NULL` или старым
артикулом.

**Собирать эти отметки в один `OR` нельзя** — точнее, можно, но на объёме это узкое место: ветки
`OR` живут на разных таблицах соединения, поэтому Postgres не может отфильтровать ни по одной из них
до `JOIN` и проверяет условие уже на готовых парах, полным перебором.

Спрашивайте «что изменилось» через `UNION ALL` по той же вьюшке — по ветке на каждую отметку:

```sql
SELECT "Number", "Year" FROM "..._rows_view" WHERE "merged_on" > :since
UNION ALL
SELECT "Number", "Year" FROM "..._rows_view" WHERE "ZakazKlienta_merged_on" > :since
UNION ALL
SELECT "Number", "Year" FROM "..._rows_view" WHERE "Nomenklatura_merged_on" > :since
```

Теперь в каждой ветке предикат ровно по одной таблице, и стоимость зависит от размера окна, а не от
размера таблиц. Переписывать сами `JOIN`-ы не нужно — логика соединений остаётся во вьюшке.

Замер на синтетике (регистр 2 млн строк, окно ~0.5%): `OR` — 620 мс, `UNION ALL` — 98 мс. Чтобы
выигрыш был, нужны две вещи: индекс по колонке, по которой витрина соединяется со справочником
(библиотека заводит только индексы по `merged_on`), и `random_page_cost = 1.1` для SSD — иначе
планировщик всё равно выберет полный скан.

### Нужно ли удалять из витрины

Чаще всего — нет, и это стоит проверить прежде, чем усложнять обработчик. **Из целевых таблиц ничего
не исчезает физически**: выпавшую из набора движений строку репликатор помечает
`is_deleted_or_empty` и гасит числовые ресурсы, у документов и справочников приезжает пометка
удаления. Если вьюшка эти строки не отфильтровывает, они доедут до витрины как обычное изменение —
достаточно upsert, а `delete_mode` остаётся дефолтным (`'no'`).

Так сделан [zakazy_klientov.py](config/handlers/zakazy_klientov.py): ключ витрины совпадает с ключом
строки регистра, поэтому пометка обновляет ту же строку витрины, а исправленная дата документа
просто меняет в ней `Period`. Удалять нечего и незачем.

Удаление нужно там, где **ключ витрины не совпадает с ключом источника** — например, агрегат по
`GROUP BY`, как в [zakazy_klientov_grouped.py](config/handlers/zakazy_klientov_grouped.py). Там
строка витрины может исчезнуть по-настоящему: переименовали `Code` — и в группе больше нет такого
`Artikul`, а старая строка осталась бы навсегда. В этом случае:

- ставьте `delete_mode='delete'` и передавайте `delete_condition`;
- **пересчитывайте группу целиком** — тот же ключ, по которому идёт удаление, а не отдельные
  «свежие» строки: иначе `delete_condition` снесёт соседние строки группы, не попавшие в инкремент;
- в пересборке блок заменяет свой отрезок целиком (`source_condition` и `delete_condition` по одному
  и тому же периоду) — это заодно чинит переезд группы между блоками.

Хранить границу обработки в самой витрине не нужно — она приходит готовой в `context.last_run_at`,
одна на все источники сразу.

## 4. Когда происходит вызов обработчика

Обработчика зовут, **когда данные подписанных таблиц действительно изменились** — что-то вставилось,
обновилось или было помечено удалённым. Одной перезаписи объекта в 1С для этого мало: она приезжает
в обмене, но если значения те же, строка в БД не меняется, `merged_on` стоит на месте, и звать
незачем — `SELECT` по окну всё равно вернул бы пусто.

Полная выгрузка объекта сигналит **на каждой сохранённой странице**, а не в конце: витрина начинает
наполняться сразу, а не через часы. Обработчику, которому это не нужно — рассылка уведомлений,
отправка в очередь, — поставьте `ON_FULL_LOAD = False`, и на страницах выгрузки его звать не будут.

Прогоны одного обработчика никогда не идут параллельно: следующий начнётся после того, как
закончится текущий. Слишком частые прогоны ограничиваются `MIN_INTERVAL` (секунды).

Отсюда же правило про `setup()`: DDL витрины и вьюшек живёт там, а не в `handle()`. `setup`
выполняется один раз за процесс, иначе `CREATE OR REPLACE VIEW` шёл бы на каждую страницу выгрузки.

## 5. Запуск обработчиков в `runner.py`

Обработчик запускает `HandlerLoop` — по циклу на каждого. Циклы блокирующие, поэтому в
[runner.py](config/runner.py) они уходят в пул потоков, рядом с репликатором:

```python
from concurrent.futures import ThreadPoolExecutor
from sqlalchemy import create_engine
from cdc_1c import HandlerLoop, Replicator1C

from handlers import ZakazyKlientov, OtpravkaVOchered

engine = create_engine(DB_URL, pool_size=6)

replicator = Replicator1C(..., engine=engine, db_schema="cdc_1c", db_temp_schema="cdc_1c_tmp")
zakazy = HandlerLoop(engine=engine, schema="cdc_1c", temp_schema="cdc_1c_tmp",
                     handler=ZakazyKlientov())
ochered = HandlerLoop(engine=engine, schema="cdc_1c", handler=OtpravkaVOchered(queue="cdc"))

with ThreadPoolExecutor(max_workers=3, thread_name_prefix='cdc') as pool:
    replicator_task = pool.submit(replicator.run_forever, interval=60)
    zakazy_task = pool.submit(zakazy.run_forever)
    ochered_task = pool.submit(ochered.run_forever)

    replicator_task.result()
    zakazy_task.result()
    ochered_task.result()
```

Что из этого следует:

- **потоков и соединений к БД нужно по числу циклов** (как считать — в
  [README_DB.md](README_DB.md), «Сколько нужно соединений к БД»);
- **порядок между обработчиками не определён**: потоки независимы, и на «витрина поверх витрины
  считается после базовой» полагаться нельзя;
- `SIGTERM` останавливает все циклы сразу, каждый — после текущего прогона; отдельный цикл
  останавливается программно через `request_stop()`;
- в `HandlerLoop` передаётся **экземпляр**, поэтому один класс можно запустить дважды с разными
  параметрами — но имена должны различаться: `ZakazyKlientov(name='ZakazyKlientov_mart2')`.

Репликатор в этом списке не обязателен. Он об обработчиках не знает — общаются они через базу,
поэтому «процесс только с обработчиками» получается вычёркиванием: убираете `Replicator1C` и его
строку в пуле. В самих обработчиках при этом не меняется ничего, и жить такой процесс может хоть в
другом контейнере.

### Несколько планов обмена

Планов обмена может быть несколько — тогда на каждый заводится свой `Replicator1C`, и все они
уходят в тот же пул потоков. Обработчику это безразлично: он не знает, сколько репликаторов его
кормит и в одном ли они с ним процессе. Единственное, что нужно помнить, — соединений к БД теперь
нужно на каждый репликатор (см. [README_DB.md](README_DB.md)).

## 6. Пересборка витрины

Иногда витрину нужно посчитать заново целиком: поменялась логика расчёта, добавили колонку, что-то
разъехалось. Для этого есть флаг в `handlers_1c`:

```sql
UPDATE cdc_1c.handlers_1c SET full_rebuild_is_required = true WHERE name = 'ZakazyKlientov';
```

Обработчик встанет в очередь сам, ждать изменений в 1С не нужно. В прогоне он увидит
`context.full_rebuild = True` и окно с начала времён (`context.last_run_at = None`), то есть тот же
`handle()` пересчитает всё. После успеха флаг снимается, а время пересборки пишется в
`last_full_rebuild_dt`.

Флаг ставится и сам — при первом запуске обработчика и когда в таблице объекта появляется новая
колонка (в 1С добавили реквизит): инкремент такую колонку не заметил бы, потому что добавление поля
не меняет `merged_on` у существующих строк.

### Пересборка по блокам

Пересборка большой витрины идёт десятками минут, и всё это время новые изменения не применяются —
витрина стоит холодной. Чтобы этого не было, нарежьте её на блоки: объявите `rebuild` — генератор,
где `yield <метка>` означает «блок закончен». Между блоками библиотека сама применит накопившиеся
изменения.

```python
def rebuild(self, context):
    for label, begin, end in self.query(context, REBUILD_BLOCKS_SQL):
        if context.rebuild_from and label <= context.rebuild_from:
            continue                      # этот месяц уже посчитан до перезапуска процесса

        with dbmerge(context.engine, table_name="ZakazyKlientov", schema=context.schema,
                     temp_schema=context.temp_schema,
                     source_table_name="ZakazyKlientov_view",
                     source_schema=context.schema) as merge:
            period = merge.source_table.c["Period"]
            merge.exec(source_condition=and_(period >= begin, period < end))

        yield label
```

Чем нарезать — решаете вы: месяц, диапазон ключей. Метка блока попадает в
`handlers_1c.rebuild_cursor` и возвращается в `context.rebuild_from`, поэтому пересборка переживает
перезапуск процесса и продолжается с того же места. Метку удобно делать сортируемой строкой
(`YYYY-MM`): точка возобновления сравнивается как строка.

Три правила, чтобы блочная пересборка была корректной:

- **блок читает данные на момент своего выполнения**, а не снимок на старте пересборки — иначе он
  затрёт изменения, применённые между блоками;
- **колонка, по которой нарезано, должна быть в самой витрине** и у каждой её строки принимать одно
  значение (в агрегате это, например, месяц из даты документа, а не период движения);
- **список блоков берите из источника и из витрины**: месяц, которого в источнике уже нет, а в
  витрине он есть, иначе не очистится — блок по нему просто не запустится.

Не объявили `rebuild` — пересборка пройдёт одним проходом, обычным `handle()`.

## 7. Что нужно помнить

- **Доставка at-least-once.** Упали после работы обработчика, но до записи `last_run_at` — окно
  повторится. Для витрины это безразлично (merge идемпотентен), для отправки во внешнюю систему
  потребитель должен быть идемпотентным.
- **Упавший обработчик границу не двигает** и остаётся «грязным» — повтор произойдёт сам, без нового
  изменения. Traceback лежит в `handlers_1c.last_error`.
- **Удаления в окно попадают.** Из целевых таблиц ничего не исчезает физически: у справочников и
  документов пометка приезжает из 1С, у регистров выпавшие из набора строки помечаются
  `is_deleted_or_empty` с обнулением ресурсов. Пометка — это `UPDATE`, который двигает `merged_on`.
  Поэтому `SELECT` обработчика **не должен** отфильтровывать `is_deleted_or_empty`: для витрины это
  строка с нулём, для очереди — событие удаления.
- **Порядок между обработчиками не определён.** Если витрина считается поверх другой витрины,
  рассчитывать на порядок нельзя — стройте её так, чтобы промежуточное состояние было допустимо.
