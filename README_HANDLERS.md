# Обработчики: свой код по событию изменения

Витрина не знает, что данные приехали: она либо опрашивает БД вхолостую по расписанию, либо ждёт,
пока её запустят руками. Репликатор это знает — он сам данные и сохранил, — поэтому он и сообщает,
что пора считать. Код, который он зовёт, и называется **обработчиком**.

Тем же способом изменения отправляют наружу: в очередь, вебхук, другую БД.

Дальше по порядку: как написать обработчик, когда его зовут, за какое окно он отвечает, где он
крутится и что нужно знать, чтобы витрина считалась правильно.

Справочник по классам и их параметрам — в [README_API.md](README_API.md), готовые разобранные
примеры — в [config/handlers/](config/handlers/), шаблон точки входа —
[config/runner.py](config/runner.py).

---

## 1. Простейший обработчик

Обработчик — обычный python-класс. Нужны две вещи: на что он подписан (`ON`) и что делать
(`handle`).

```python
from cdc_1c import Handler1C

class ZakazyKlientov(Handler1C):
    # имена ТАБЛИЦ в целевой БД (транслит), а не имена объектов 1С
    ON = ["AccumulationRegister_ZakazyKlientov", "Catalog_Nomenklatura"]

    def setup(self, context):        # один раз за процесс: DDL витрины и вьюшек
        self.execute(context, DDL)

    def handle(self, context):       # полезная работа
        self.execute(context, """
            insert into {schema}."mart_zakazy" (...)
            select ... from {schema}."AccumulationRegister_ZakazyKlientov"
            where merged_on > :since
        """, since=self.since(context))
```

Подключается явным списком — никакого сканирования каталогов:

```python
from cdc_1c import HandlerLoop
from handlers import ZakazyKlientov, OtpravkaVOchered

handler_zakazy = HandlerLoop(engine=engine, schema="cdc_1c", handler=ZakazyKlientov())
handler_ochered = HandlerLoop(engine=engine, schema="cdc_1c",
                              handler=OtpravkaVOchered(queue="cdc"))

with ThreadPoolExecutor(max_workers=2) as pool:
    pool.submit(handler_zakazy.run_forever)
    pool.submit(handler_ochered.run_forever)
```

Никакого особого каталога обработчикам не нужно: это обычные python-модули, лежат где угодно, лишь
бы импортировались, а общий код между ними подключается обычным `import`. Обновление библиотеки этот
код не трогает.

### Что можно объявить

| объявление | смысл |
|---|---|
| `ON` | список таблиц, на изменение которых подписан. Обязательно |
| `NAME` | имя в `handlers_1c`; по умолчанию имя класса |
| `ON_FULL_LOAD` | звать ли на страницах полной выгрузки (по умолчанию `True`) |
| `MIN_INTERVAL` | не чаще одного прогона в N секунд |

`ON` — это не только «на что реагировать», но и «что я читаю»: по этому же списку считается верхняя
граница окна. Перечислять надо **все** таблицы, из которых обработчик выбирает данные.

Имена в `ON` — те, что видны в БД (`Catalog_Nomenklatura`), а не имена 1С
(`Catalog_Номенклатура`): обработчик пишет SQL по таблицам, имени 1С он в глаза не видит. Имя 1С не
совпало бы ни с чем, и обработчик молча не сработал бы никогда — поэтому такой список отвергается на
старте, с подсказкой, как это имя выглядит в базе.

В `HandlerLoop` передаётся **экземпляр**, а не класс: так обработчик можно параметризовать
конструктором (одна логика на две схемы — два экземпляра). Имя служит ключом состояния в
`handlers_1c`, поэтому у параметризованных экземпляров оно обязано различаться:
`ZakazyKlientov(name='ZakazyKlientov_mart2')`. Одноимённые отвергаются на старте.

Наследоваться от `Handler1C` не обязательно — достаточно `ON` и `handle`, годится и модуль целиком,
и функция с этими атрибутами. Базовый класс просто снимает копипасту: `since(context)`,
`changed_since(context, *колонки)`, `execute(context, sql)`, `query(context, sql)`. В `sql` двух
последних `{schema}` подставляется целевой схемой.

## 2. Окно изменений — главное понятие

**Данные обработчику не передаются.** Ему передаётся окно времени, за которое надо отработать, а
`SELECT` он делает сам:

```sql
WHERE merged_on > :last_run_at
```

Так он не зависит от того, каким путём данные приехали — изменением или полной выгрузкой, — и не
обязан разбирать чужой формат.

| поле `context` | что это |
|---|---|
| `last_run_at` | отметка предыдущего **успешного** прогона; `None` — с начала времён |
| `boundary` | верхняя граница окна: то, что станет `last_run_at` в следующий раз |
| `full_rebuild` | витрину просят собрать заново (см. §6) |
| `rebuild_from` | метка последнего завершённого блока пересборки (см. §6) |
| `engine`, `schema`, `temp_schema` | подключение и схемы |
| `logger` | логгер обработчика |
| `objects`, `sources` | **только для логов**, см. ниже |

Обе границы — по часам БД (тем же `now()`, которым `dbmerge` штампует `merged_on`), поэтому
расхождение часов между хостами роли не играет.

`objects` и `sources` точности не несут, и это осознанно: репликатор сообщает об изменении меткой
времени, а метка не содержит ни имени таблицы, ни источника. Поэтому `objects` — это весь `ON`
обработчика, а `sources` — `db_signal` (изменение), `startup` (первый проход процесса) или
`full_rebuild` (заказ пересборки). Отличить по ним бэкфилл полной выгрузки от живого изменения
нельзя — для этого есть `ON_FULL_LOAD`.

### Почему в `WHERE` нет верхней границы

Окно закрывается справа, но в условие выборки это писать не нужно. От пропуска строк защищает не
`WHERE`, а само значение `boundary`: оно прижато к старту незавершённого merge, чьи строки
обработчику всё равно не видны.

Видимую строку правее границы обработчик посчитает раньше срока — и посчитает ещё раз в следующем
окне, потому что `last_run_at` станет `boundary`. Это лишняя работа, а не пропуск, и взамен витрина
получается свежее.

Добавлять `merged_on <= :boundary` имеет смысл только там, где повтор дорог сам по себе — например,
при отправке во внешнюю систему.

## 3. Когда обработчика зовут

**Только когда merge реально что-то изменил** — вставил, обновил или пометил удалённой хоть одну
строку. 1С регистрирует изменение объекта на любую перезапись, и в пакет приезжает масса записей,
идентичных тому, что уже лежит в БД; шумные поля (версия данных, номер сообщения обмена) при
сравнении не учитываются. Звать на таком пакете незачем — `SELECT` по окну всё равно вернёт пусто.

**Полная выгрузка сигналит на каждую сохранённую страницу**, а не один раз в конце. Лишних вызовов
это не даёт (метка просто перезаписывается), зато витрина начинает наполняться после первой же
страницы, а не через часы. Обработчику, которому бэкфилл не нужен — рассылка уведомлений, отправка в
очередь, — ставьте `ON_FULL_LOAD = False`: он объявляет это в `handlers_1c`, и на страницах выгрузки
репликатор его просто не трогает.

По той же причине DDL живёт в `setup()`, а не в `handle()`: `setup` вызывается один раз за процесс,
иначе `CREATE OR REPLACE VIEW` выполнялся бы на каждую страницу выгрузки.

Пользовательский код никогда не выполняется в потоках репликатора: тот только ставит метку в
`handlers_1c`.

## 4. Где обработчик крутится

`run_forever` у обработчика блокирующий — ровно как у репликатора, поэтому запускаются они
одинаково, и где именно крутиться, решает точка входа. Останавливает всех `SIGTERM`; отдельный
цикл — `request_stop()`.

`HandlerLoop` — цикл **одного** обработчика: его состояние и его прогоны. По циклу на обработчика,
чтобы тяжёлая витрина не задерживала остальные. Обратная сторона: **порядок между обработчиками не
определён** — потоки независимы, и на «витрина поверх витрины считается после базовой» полагаться
нельзя. Два обработчика, пишущие в одну целевую таблицу, тоже могут делать это одновременно.

Репликатору обработчиков **не передают**: он о них не знает и знать не должен. Поэтому поднять их
можно где угодно — в одном процессе с репликатором, в соседнем или в другом контейнере. Процесс
«только обработчики» получается из [runner.py](config/runner.py) вычёркиванием: убираете
`Replicator1C` и его строку в пуле, остаются одни `HandlerLoop`. В самих обработчиках не меняется
ничего.

### Сколько нужно соединений к БД

Потоков несколько сортов, и занять чужие они не могут, но `engine` у них общий, и держать соединение
одновременно могут все сразу: цикл изменений, `full_load_workers` потоков полной выгрузки, поток
отметки живости незавершённых merge, по потоку на каждого обработчика и по потоку на каждое
расписание (`FullLoadCron` пишет страницы сам, а не через пул выгрузки).

```
pool_size >= full_load_workers + 2 + число обработчиков + число расписаний в этом процессе
```

Не хватает соединений — кто-то встаёт в ожидание, и затормозить может как обработчик, так и сама
выгрузка. Если обработчики вынесены в отдельный процесс, у каждого процесса свой `engine` и свой
счёт.

### Несколько планов обмена

На каждый план обмена заводится свой `Replicator1C`. Обработчику это безразлично: сколько планов его
кормит и в одном ли они с ним процессе, он не знает. Все репликаторы ставят метку в те же
`handlers_1c` и публикуют свои незавершённые merge в общую `writes_in_process_1c`.

Если репликаторы живут в одном процессе, помните: `run_forever` блокирует поток, так что второй
запускается в своём. Пул тогда считается по сумме:

```
sum(full_load_workers) + 2 × число репликаторов + число обработчиков + число расписаний
```

## 5. Как это устроено внутри

Через базу, и только через неё. Обработчик при старте объявляет себя в `handlers_1c` и записывает в
`update_on` таблицы, на которые подписан. Репликатор эту колонку читает и, увидев изменение
подписанной таблицы, ставит в `update_requested_at` момент сигнала — а дальше обработчик сам
замечает метку своим циклом и снимает её успешным прогоном.

```
репликатор            handlers_1c                обработчик
──────────            ───────────                ──────────
сохранил объект  →  update_requested_at=время  →  увидел метку, посчитал витрину,
                                                  снял её и записал last_run_at
```

Метка времени, а не булев флаг, — из-за сигнала, пришедшего **посередине прогона**: поднять `true`
над `true` нельзя, следа не остаётся, и прогон снимал флаг вместе с непрочитанным сигналом — витрина
отставала до следующего изменения, молча. Метку прогон снимает, только если она не правее границы
его окна; всё, что правее, он не читал, и оно заводит его ещё раз.

Верхняя граница окна тоже берётся из базы — из таблицы `writes_in_process_1c`, куда репликатор пишет
свои незавершённые merge. Обработчик обязан их видеть, чей бы процесс их ни начал: их строки уже
имеют `merged_on` в прошлом, но ещё не видны, и граница, взятая как «сейчас», их бы перешагнула.
Строки умершего процесса отсекаются по отметке живости — она обновляется, пока репликатор жив,
поэтому его падение обработчиков не морозит.

### Таблица состояния `handlers_1c`

| колонка | смысл |
|---|---|
| `name` | `NAME`, либо имя класса обработчика |
| `update_on` | таблицы, на которые подписан; заполняет обработчик, читает репликатор |
| `on_full_load` | звать ли на страницах полной выгрузки; тоже объявляет обработчик |
| `update_requested_at` | момент сигнала; `NULL` — незакрытых сигналов нет |
| `enabled` | выключенный обработчик не зовут (и окно за время простоя не копят) |
| `last_run_at` | граница последнего успешного запуска |
| `last_error` | traceback последнего падения |
| `full_rebuild_is_required` | заказ на пересборку витрины |
| `rebuild_cursor` | метка последнего завершённого блока идущей пересборки; `NULL` — пересборка не идёт |
| `last_full_rebuild_dt` | когда пересборка отработала в последний раз |
| `last_full_rebuild_minutes` | сколько она заняла, минуты (дробное) |

## 6. Пересборка витрины

Попросить собрать заново:

```sql
UPDATE cdc_1c.handlers_1c SET full_rebuild_is_required = true WHERE name = 'ZakazyKlientov';
```

Заказ сам ставит обработчика в очередь — ждать изменений по подписанным объектам не нужно. Он
получит окно с начала времён (`context.last_run_at` = `None`) и `context.full_rebuild` = `True`.
Первый в жизни прогон — тоже пересборка, флаг для этого ставить не нужно. После успеха требование
снимается, а время пишется в `last_full_rebuild_dt`; `last_run_at` при этом не обнуляется — упавшая
пересборка не теряет прежнюю границу.

Тот же заказ репликатор ставит сам, когда в таблице объекта появляется **новая колонка** (новый
реквизит в 1С). Инкремент её не увидел бы никогда: окно строится по `merged_on`, а он двигается
только у строк, где изменились значения — добавление колонки не меняет ни одного значения, и все уже
лежащие строки остались бы левее окна навсегда.

### Пересборка по блокам

Пересборка большой витрины идёт десятками минут, и всё это время изменения не применяются — витрина
стоит холодной. Чтобы этого не было, объявите `rebuild` — генератор, где `yield <метка>` означает
«блок закончен и закоммичен». В этих точках цикл вклинивается и применяет накопившиеся изменения.

```python
def rebuild(self, context):
    for year in self.years(context):
        if context.rebuild_from and str(year) <= context.rebuild_from:
            continue                      # этот год уже посчитан до перезапуска процесса
        self.merge_year(context, year)
        yield str(year)
```

Чем нарезать — решает обработчик: период, диапазон ключей, склад, организация. Библиотека в блоки не
заглядывает; метка нужна ей только чтобы записать её в `rebuild_cursor` и вернуть в
`context.rebuild_from` после перезапуска — генератор живёт в памяти и рестарта не переживает, а
начинать сорокаминутную пересборку заново из-за этого не хочется. Метку удобно делать сортируемой
строкой (`YYYY-MM`): точка возобновления сравнивается именно как строка.

Не объявили `rebuild` — прежнее поведение: один проход, весь `handle()` целиком.

**Почему это безопасно и почему это не параллельность.** Блок и инкремент выполняет один и тот же
поток, поэтому одновременно они не работают никогда — затирать друг друга им нечем. Считай
пересборка в своём потоке, случилось бы именно это: она читает данные в момент старта, а коммитит
десятки минут спустя, и её `delete_condition` снёс бы группу целиком вместе со свежим результатом
инкремента. Причём **безвозвратно**: инкремент уже сдвинул `last_run_at` за это изменение, и группу
никто не пересчитает, пока источник не изменится снова. Платим за безопасность задержкой в один блок
вместо задержки во всю пересборку.

Отсюда единственное требование к блоку: он должен читать данные **актуальные на момент своего
выполнения**, а не снимок на старте пересборки. Обработчики так и написаны (верхней границы в
`WHERE` у них нет), поэтому специально делать ничего не нужно — но «прочитаю всё один раз в начале,
разложу по блокам потом» сломает ровно это.

Блок устроен проще инкремента, и это не случайность: инкремент видит лишь часть строк блока и
поэтому обязан аккуратно выбирать, что пересчитать, — а блок видит их все и просто **заменяет блок
целиком**:

```python
merge.exec(source_condition=source_period == period,
           delete_condition=target_period == period)
```

Заодно это само чинит переезд между блоками (поправили дату документа): из старого месяца строку
удалит его блок, в новом создаст его собственный.

Отсюда требование к колонке, по которой нарезано: она должна быть **в самой витрине** и у каждой её
строки принимать одно значение. В [zakazy_klientov_grouped.py](config/handlers/zakazy_klientov_grouped.py)
это видно хорошо: витрина агрегатная, поэтому месяц берётся из даты документа (из неё же берётся
`Year` в ключе группы, значит у группы он ровно один), а не из периода движения, которых у группы
может быть несколько.

Список блоков берите из источника **и из витрины**: месяц, которого в источнике больше нет, а в
витрине он есть, иначе не очистится никогда — блок по нему просто не запустится.

## 7. Как писать саму витрину

1С хранит данные нормализованно: чтобы дотянуться из регистра заказов до кода товара, нужен `JOIN`
со справочником номенклатуры по guid. Для задач DWH обычно нужна менее строгая нормализация, поэтому
в [config/handlers/](config/handlers/) лежат два разобранных примера инкрементальной витрины:

- [zakazy_klientov.py](config/handlers/zakazy_klientov.py) — ключ таблицы фактов сохраняется (строки
  регистра как есть, плюс артикул из справочника);
- [zakazy_klientov_grouped.py](config/handlers/zakazy_klientov_grouped.py) — ключ меняется
  (`GROUP BY` по номеру документа, году и артикулу), пересчёт остаётся инкрементальным, а ключ
  группы составной — видно, как это отражается на фильтрах (`tuple_(a, b).in_(...)`).

**Отметка времени нужна от каждого участника `JOIN`.** Оба примера построены на одном правиле:
вьюшка отдаёт `merged_on` каждого источника отдельной колонкой (`merged_on`,
`Nomenklatura_merged_on`, …), и в инкремент попадает всё, что стало свежее хотя бы по одному из них.

Так надо потому, что объекты 1С приезжают в обмене независимо и в произвольном порядке: справочник
номенклатуры может доехать или измениться позже регистра. Если ориентироваться только на `merged_on`
регистра, такая строка в инкремент не попадёт, и витрина навсегда останется с `NULL` или старым
артикулом.

**Собирать эти отметки в один `OR` нельзя.** Ветки `OR` живут на разных таблицах соединения, поэтому
ни по одной нельзя отфильтровать до `JOIN`: условие проверяется на готовой паре и вырождается в
`Join Filter` поверх полного соединения. `BitmapOr` из индексных сканов Postgres строит только когда
все ветки на одной таблице, а переписать `OR` в `UNION` через границу джойна он не умеет.

Поэтому «какие группы изменились» спрашивается через `UNION ALL` по той же вьюшке — по ветке на
отметку:

```sql
SELECT "Number", "Year" FROM "..._rows_view" WHERE "merged_on" > :since
UNION ALL
SELECT "Number", "Year" FROM "..._rows_view" WHERE "ZakazKlienta_merged_on" > :since
UNION ALL
SELECT "Number", "Year" FROM "..._rows_view" WHERE "Nomenklatura_merged_on" > :since
```

В каждой ветке остаётся предикат ровно по одной базовой таблице, планировщик опускает его внутрь
вьюшки, в скан этой таблицы, и стоимость начинает зависеть от размера окна, а не от размера таблиц.
Переписывать `JOIN`-ы руками при этом не нужно — логика соединений остаётся в одном месте.

На синтетике (регистр 2 млн строк, окно ~0.5%): `OR` — 620 мс с полным сканом регистра,
`UNION ALL` — 98 мс без единого `Seq Scan`. Двух вещей это требует: `random_page_cost` под SSD
(`1.1` вместо дефолтных `4`, иначе планировщик всё равно предпочтёт полный скан) и индекса по
колонке соединения со справочником — репликатор создаёт только индексы по `merged_on`, а что с чем
соединяется, знает витрина.

**Пересчитывать нужно группу целиком** — тот же ключ, по которому идёт удаление, а не отдельные
«свежие» строки: иначе `delete_condition` снесёт соседние строки группы, которые в инкремент не
попали.

Хранить границу обработки в самой витрине не нужно — она приходит готовой в `context.last_run_at`,
одна на все источники сразу.

---

## 8. Что нужно помнить

- **Доставка at-least-once.** Упали после работы обработчика, но до записи `last_run_at` — окно
  повторится. Для витрины это безразлично (merge идемпотентен), для отправки во внешнюю систему
  потребитель должен быть идемпотентным.
- **Упавший обработчик границу не двигает** и остаётся «грязным» — повтор произойдёт сам, без нового
  изменения. Traceback лежит в `handlers_1c.last_error`.
- **Удаления в окно попадают.** Из целевых таблиц ничего не исчезает физически: у справочников и
  документов пометка приезжает из 1С, у регистров выпавшие из набора строки помечаются
  `is_deleted_or_empty` с обнулением ресурсов. Пометка — это `UPDATE`, который двигает `merged_on`.
  Поэтому `SELECT` обработчика **не должен** отфильтровывать `is_deleted_or_empty`: для витрины это
  строка с нулём, для очереди — событие удаления.
- **Порядок между обработчиками не определён.** Если витрина считается поверх другой витрины,
  рассчитывать на порядок нельзя — стройте её так, чтобы промежуточное состояние было допустимо.
