# API: классы, которые собирает пользователь

Справочник по тому, из чего собирается точка входа: что принимает каждый класс, что у него можно
вызвать и чем именно он занят. Здесь только публичная часть — внутренние `DataReader1C`,
`DBWriter1C`, `MetadataReader1C` и прочие вызываются библиотекой сами, и трогать их не нужно.

Обзор и запуск — в [README.md](README.md), переменные окружения — в [README_ENV.md](README_ENV.md),
что появляется в БД — в [README_DB.md](README_DB.md), внутреннее устройство (OData, цикл
изменений, полная выгрузка, обработчики) — в [DESIGN.md](DESIGN.md). Готовый шаблон сборки —
[config/runner.py](config/runner.py).

Всё импортируется из корня пакета:

```python
from cdc_1c import Replicator1C, HandlerLoop, Handler1C, HandlerContext, FullLoadCron
```

Общее правило по именам объектов: `Replicator1C` работает с именами **1С**
(`Document_ЗаказКлиента`), а обработчики и расписания — с именами **таблиц** в БД
(`Document_ZakazKlienta`, латиница из `metadata_objects_1c.object_full_name_en`).

## `Replicator1C` — чтение изменений и запись в БД

Оркестратор: читает изменения из 1С (OData + план обмена) и пишет их в целевую БД, подтверждая
приём пакета только после успешного сохранения. Он же исполнитель полной выгрузки.

```python
Replicator1C(
    odata_url: str,                       # адрес OData-интерфейса базы 1С
    odata_auth: tuple[str, str] | None,   # (пользователь, пароль); None — без авторизации
    exchange_name: str,                   # имя плана обмена в 1С
    queue_guid: str,                      # Ref_Key узла обмена; пустой — список узлов в лог
    engine: Engine,                       # готовый SQLAlchemy Engine, не строка подключения
    db_schema: str | None = None,         # None — схема БД по умолчанию
    db_temp_schema: str | None = None,    # схема промежуточных таблиц merge; None — схема данных
    request_timeout: float | None = None, # таймаут HTTP к 1С, сек
    full_load_workers: int = 2,           # фоновых потоков полной выгрузки
)
```

Параметры проверяются прямо в конструкторе: ошибка конфигурации падает сразу и с внятным текстом,
а не в середине первого цикла. `engine` передаётся готовым намеренно — пул и его размер задаёт
приложение (см. [README_DB.md](README_DB.md), «Сколько нужно соединений к БД»).

| метод | что делает |
|---|---|
| `run_forever(interval=60.0, max_iterations=0, max_backoff=1800.0)` | цикл `run_once` с паузой `interval`. Упавший цикл логируется и повторяется с нарастающей паузой; ошибки прав и адреса уводят паузу на потолок сразу. После каждого цикла фоном идут полные выгрузки помеченных объектов. Блокирующий; останавливается по SIGTERM/SIGINT |
| `run_once(notify_changes=True)` | один цикл: read → save → notify. `notify_changes=False` не подтверждает пакет — изменения остаются в очереди 1С, прогон повторяемый (так работают живые тесты) |
| `full_load(object_name, batch_size=1000, date_field=None, date_from=None, date_to=None, mark_missing=False)` | полная выгрузка объекта; возвращает число **реально изменённых** строк. При исправном CDC это 0 — им и проверяют, что изменения доезжают. Имя объекта — как в 1С |
| `list_objects()` | состав плана обмена: какие объекты 1С вообще приедут |
| `request_stop()` | попросить идущий `run_forever` завершиться после текущей итерации (для репликатора не в главном потоке — свой перехват сигналов ему поставить нельзя) |
| `claim_full_load(object_full_name)` | контекстный менеджер: занять объект под выгрузку. Отдаёт `False`, если его уже выгружает кто-то другой. Нужен тем, кто пишет своё расписание |

`batch_size` — верхняя граница, а не размер страницы: реальный подбирается по весу ответа.
Глубокий объект дополнительно режется на месяцы — оба механизма разобраны в [DESIGN.md](DESIGN.md).

`mark_missing=True` помечает строки, которых в 1С больше нет: физическое удаление объекта в обмен
не приходит вовсе, и иначе такие строки остаются в таблице навсегда. По умолчанию выключено —
прогон становится дороже.

## `Handler1C` — свой код по событию изменения

Базовый класс обработчика: считает витрину или отправляет данные во внешнюю систему, когда merge
реально изменил подписанные таблицы. Наследование необязательно — годится и модуль, и функция,
нужны только `ON` и `handle`; базовый класс лишь снимает копипасту.

```python
class ZakazyKlientov(Handler1C):
    ON = ["AccumulationRegister_ZakazyKlientov"]   # имена ТАБЛИЦ, не объектов 1С

    def handle(self, context: HandlerContext) -> None:
        self.execute(context, 'insert into ... where merged_on > :last_run_at',
                     last_run_at=context.last_run_at)
```

Аннотация `context: HandlerContext` не обязательна, но с ней IDE подсказывает поля контекста и их
типы — писать её стоит везде.

| объявление | смысл |
|---|---|
| `ON` | таблицы, на изменение которых подписан обработчик. Обязательно |
| `NAME` | имя в `handlers_1c`; по умолчанию имя класса. Ключ состояния — два одноимённых поделят одну отметку |
| `ON_FULL_LOAD` | вызывать ли на страницах полной выгрузки (по умолчанию да) |
| `MIN_INTERVAL` | не чаще одного прогона в N секунд |

| метод | когда вызывается |
|---|---|
| `setup(context)` | один раз за процесс, до первого прогона: DDL витрины, создание вьюшек |
| `handle(context)` | обычный прогон за окно `(last_run_at, boundary]`. Обязателен |
| `rebuild(context)` | необязательный генератор полной пересборки: `yield <метка>` означает «блок закончен», между блоками библиотека применяет накопившиеся изменения. Не объявлен — пересборка идёт одним проходом |

Помощники, чтобы не писать одно и то же:
`changed_since(context, *columns)` — условие «изменилось за окно» для SQLAlchemy;
`execute(context, sql, **params)` и `query(context, sql, **params)` — SQL с параметрами на движке
контекста; `schema_prefix(context)` — префикс схемы для строкового SQL.

Данные обработчику **не передаются**: он получает окно по часам БД и выбирает изменившееся сам.
Как это работает и что нужно знать, чтобы витрина считалась правильно, — в docstring модуля
`cdc_1c.handlers`, а механика (сигнал, граница окна, пересборка блоками) — в
[DESIGN.md](DESIGN.md#обработчики-сигнал-окно-и-пересборка).

### `HandlerContext` — что обработчик получает

| поле | значение |
|---|---|
| `engine`, `schema`, `temp_schema` | подключение и схемы (те же, что у `HandlerLoop`) |
| `last_run_at`, `boundary` | границы окна: `(last_run_at, boundary]` — за него обработчик и отвечает. Обе всегда `datetime`: первый прогон и пересборка получают в `last_run_at` начало времён (`EPOCH`), а не `None` |
| `full_rebuild`, `rebuild_from` | идёт ли пересборка и метка последнего завершённого блока |
| `objects`, `sources` | какие таблицы изменились и откуда пришёл сигнал (`changes` / `full_load` / …) |
| `logger` | логгер обработчика |

## `HandlerLoop` — цикл одного обработчика

Запускает обработчика: следит за меткой сигнала в `handlers_1c`, считает окно, вызывает `handle` и
записывает результат. На каждого обработчика заводится свой цикл, поэтому тяжёлая витрина не
задерживает остальные.

```python
HandlerLoop(
    engine: Engine,
    schema: str | None,
    handler,                              # экземпляр Handler1C, модуль или функция
    temp_schema: str | None = None,       # уедет в context.temp_schema
)
```

Есть ещё служебный `write_tracker` — цикл заводит его себе сам, задавать нужно только в тестах.

| метод | что делает |
|---|---|
| `run_forever(poll_interval=1.0)` | блокирующий цикл, как у репликатора; останавливается тем же SIGTERM |
| `run_if_pending()` | один прогон, если есть непрочитанный сигнал. Для своего планировщика или тестов |
| `request_stop()` | остановиться после текущего прогона |

Репликатор об обработчиках не знает: связывает их только БД (`handlers_1c`). Отсюда и свобода
раскладки — обработчиков можно поднять отдельным процессом или в другом контейнере.

## `FullLoadCron` — полная выгрузка по расписанию

Вечный цикл того же покроя, что у репликатора: по crontab-расписанию запускает `full_load`
объекта. Нужен затем, что цикл изменений догоняет данные событиями, а полная выгрузка — сверяет:
при исправном CDC она отвечает нулём изменённых строк, а ненулевой ответ показывает расхождение
и тут же его выравнивает.

```python
FullLoadCron(
    replicator,                           # тот же Replicator1C — он исполнитель выгрузки
    table_name: str,                      # имя ТАБЛИЦЫ (латиница); имя 1С тоже принимается
    *,
    cron: str,                            # обычная crontab-строка; время локальное (см. TZ)
    date_field: str | None = None,        # поле даты для фильтра по периоду
    date_from=None, date_to=None,         # границы: дата, дата-время, ISO-строка или timedelta
    batch_size: int = 1000,
    mark_missing: bool = False,
)
```

`timedelta` в границе даёт скользящее окно: `date_from=timedelta(days=3)` — «последние трое суток»,
считается в момент срабатывания. Объект, который уже выгружается (фоновая выгрузка репликатора или
другое расписание), пропускается с предупреждением — 1С не получает двойную работу.

| метод | что делает |
|---|---|
| `run_forever(max_runs=0)` | блокирующий цикл по расписанию |
| `run_once()` | сработать немедленно — проверить настройку, не дожидаясь трёх часов ночи |
| `request_stop()` | остановиться после текущего прогона |

Каждое расписание работает своим потоком, поэтому `pool_size` нужен на единицу больше за каждое.
